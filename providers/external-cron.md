# 외부 cron SaaS — 2차 스케줄러 겸 감시견

- **last-verified**: 2026-10-18

## 먼저: 능동 호출형이어야 한다

| 유형 | 예 | 깨울 수 있나 |
|------|-----|--------------|
| **수동 수신** | healthchecks.io, Cronitor(모니터링 모드) | ❌ |
| **능동 호출** | cron-job.org, UptimeRobot | ✅ |

**healthchecks.io는 2차 스케줄러가 될 수 없다.** 공식 문서가 *"monitoring website
uptime by probing it with HTTP requests"* 용도에는 **부적합**하다고 명시한다. 핑을
받아 "안 오면 알려주는" 서비스라, 핑을 보낼 주체가 반드시 따로 필요하다.

→ 감시견으로는 훌륭하지만 **단독으로는 성립하지 않는다.** 많은 가이드가 이 둘을 섞는다.

## 능동 호출형 비교

| | cron-job.org | UptimeRobot |
|---|---|---|
| 무료 범위 | 작업 수 무제한(fair use) | 모니터 50개 |
| 최소 주기 | **1분** | 5분 |
| 실행 타임아웃 | 30초 (무료) | — |
| 오픈소스 | ✅ **GPL-2.0** | ❌ |
| 운영 | 개인(Patrick Schlangen), **15년+**, 기부 기반 | 상업 회사 (유료 플랜이 재원) |
| SLA | **없음** | 유료 플랜 기준 존재 |

## 왜 cron-job.org를 기본 추천하나

**신뢰도가 높아서가 아니라 신뢰가 필요 없는 구조로 쓰기 때문이다** (README 원칙 2).

맡기는 것이 비밀 없는 무해한 URL뿐이면, 업체가 털려도·악의적이어도·사라져도 잃을 게
없다. 그 전제 위에서는 무료·오픈소스·탈출 가능(자체 호스팅)이 SLA보다 실용적이다.

⚠ 단 **기부 기반이라 SLA가 없다.** 단독 의존 금지 — 1차는 플랫폼 내장 크론을 유지한다.

## 설정 체크리스트 (cron-job.org 기준)

**COMMON**
- URL: `https://<도메인>/api/wake?via=cronjoborg` — `?via=` 로 로그에서 출처 구분
- 스케줄: **하루 1회** (기본값이 `*/15` = 하루 96회이므로 반드시 변경)
- 시간대: 작업별 지정이므로 **입력값이 곧 현지 시각** (Vercel의 UTC와 혼동 주의)
- Save responses: 초기엔 ON (응답에 비밀이 없으므로 안전, 디버깅에 유용)

**NOTIFICATIONS** — 여기가 감시견의 본체다. 비워두면 그냥 중복 크론이다.

| 옵션 | 값 | 이유 |
|------|-----|------|
| 실패 시 알림 | ON, **1회** | 하루 1회 실행이라 "2회 실패 후"는 이틀을 날린다 |
| 복구 시 알림 | ON | 스스로 나았는지 확인하러 들어가지 않아도 된다 |
| **자동 비활성 시 알림** | **ON** | 반복 실패하면 작업이 자동 비활성된다. 꺼져 있으면 **2차가 조용히 사라진다** |
| TLS 만료 알림 | ON (덤) | 도메인 인증서 만료 경고를 공짜로 얻는다 |

**ADVANCED**
- 메서드 GET, 타임아웃 기본값
- **헤더·인증은 비워 둘 것** — 넣을 게 없게 설계한 것이 요점이다 (README 원칙 2)

## 검증

저장 후 [Test run] → 200. 그리고 **대상 서비스 로그에서 실제 도달을 확인**할 것.

실측 예 (2026-10-18):
```
[wake] via=cronjoborg ua=Mozilla/4.0 (compatible; cron-job.org; http://cron-job.org/)
GET 200 /api/wake
```
