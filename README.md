# keepalive-kit

> 원본은 `blog-thinknormal` 의 `tools/keepalive-kit` — **레퍼런스 구현이 실제로
> 돌고 있는 곳**이다. 여기 적힌 실측값은 전부 그 운영 환경에서 나왔다.
> 공개본은 `git subtree split --prefix=tools/keepalive-kit` 으로 추출한다.

무료 티어 서비스가 **방치되면 잠드는 문제**를 다루는 플레이북.

Supabase 무료 플랜은 7일 무활동이면 프로젝트를 정지시킨다. 비슷한 정책이 Neon·Render·
Fly·Railway에도 있다. MVP를 만들어 두고 몇 주 손을 떼면 돌아왔을 때 죽어 있다.

해결 자체는 간단하다 — 주기적으로 가벼운 쿼리를 날리면 된다. 코드로 치면 열 줄이다.
**어려운 건 코드가 아니라 그 주변의 함정들이다.**

---

## 이 문서가 기존 가이드와 다른 점

"GitHub Actions로 크론 걸면 된다"는 글은 많다. 그런데 그 글들은 대개 이걸 안 적는다:

> **GitHub Actions 스케줄은 60일 무커밋이면 자동 비활성된다.
> 워크플로 실행은 "활동"으로 인정되지 않는다.**

즉 **잠들지 않게 하려고 쓴 장치가 같은 이유로 잠든다.** 정확히 MVP 방치 시나리오에서
터지고, 터져도 조용하다.

이 저장소는 그런 **실측으로만 알 수 있는 함정**을 모은다. 각 사실에는 `last-verified`
날짜가 붙고, `scripts/doctor.mjs`가 그 주장들을 **실제로 다시 확인**한다.

---

## 핵심 원칙 8가지

실제 구축 과정에서 깨지면서 얻은 것들이다. 각 항목의 근거는 `providers/`에 있다.

### 1. 수면 방지 장치를 고르기 전에, 그 장치 자신의 수면 조건을 본다

| 장치 | 자신의 정지 조건 |
|------|------------------|
| Supabase 무료 | 7일 무활동 |
| **GitHub Actions 스케줄** | **60일 무커밋** (워크플로 실행은 활동 아님) |
| Vercel Cron | 없음 — 배포가 살아 있으면 계속 |
| 외부 cron SaaS | 없음 — 계정만 유지 |

→ **GitHub Actions는 이중화로 부적합하다.** 7일짜리와 60일짜리가 방치 시 순차적으로
죽으므로 실패 모드가 독립이 아니다.

### 2. 외부에 맡길 엔드포인트는 "털려도 괜찮게" 설계한다

> 비밀을 쥔 URL을 제3자에게 맡기는 순간 **그 업체의 보안이 당신의 보안이 된다.**

```
❌ /api/cron/keep-alive?secret=xxx  를 외부 cron 서비스에 등록
   → 비밀이 제3자 DB에 저장된다

✅ 비밀 없는 무해한 엔드포인트를 따로 판다
   → 업체 선택이 "신뢰 문제"에서 "가용성 문제"로 격하된다
```

무해함의 기준: 하는 일이 `select 1` 한 번. 읽기도 쓰기도 아니고 데이터를 반환하지
않는다. **남용의 최대치가 "DB를 깨우는 것"인데 그게 엔드포인트의 목적이다.**

### 3. 감시견은 능동/수동을 구분해서 고른다

| 유형 | 예 | 깨울 수 있나 |
|------|-----|--------------|
| **수동 수신** | healthchecks.io | ❌ 핑을 받기만 한다. 보낼 주체가 따로 필요 |
| **능동 호출** | cron-job.org, UptimeRobot | ✅ URL을 호출하고 실패 시 알린다 |

많은 가이드가 이 둘을 섞어 쓴다. **능동 호출형 하나면 깨우기와 감시를 동시에 한다.**

### 4. 알림 채널의 가시성을 먼저 확인한다

공개 ntfy는 **토픽 이름만 알면 누구나 지난 메시지까지 읽는다**:

```bash
curl "https://ntfy.sh/<topic>/json?poll=1&since=all"
```

→ 알림 본문에 **제3자 개인정보를 싣지 않는다.** 알림은 "볼 것이 생겼다"는 신호까지만.

### 5. 알림의 링크 목적지는 "그 알림이 뜬 상황"에서 동작해야 한다

`DB 응답 실패` 알림이 관리자 대시보드로 링크돼 있으면, 탭했을 때 **바로 그 이유로 깨진
페이지**를 보게 된다(대시보드도 DB를 쓰므로).

→ 장애 알림은 장애 상황에서도 의미 있는 응답을 주는 곳으로 보낸다.

### 6. 관측 가능성은 설계 요소다

Vercel Hobby 기준:

- 런타임 로그 보존 **1시간**
- 크론 실행 정밀도 **시(hour) 단위 ±59분**
- 전달은 **best effort** — 누락 시 로그조차 남지 않는다

→ **"로그에 없다"가 "실패했다"를 뜻하지 않는다.** 성공 후 보존 만료 / 인증 실패 /
아예 미실행, 셋 다 가능하다.

이중화는 신뢰성뿐 아니라 **가시성**도 올려 준다 — 외부 스케줄러는 자체 대시보드에
실행 이력이 남기 때문이다.

### 7. 문서보다 실측을 믿는다

공식 문서대로 짰다가 깨진 실제 사례:

> ntfy 예약 메시지는 `DELETE /<topic>/<id>`로 취소할 수 있다고 문서에 적혀 있다.
> 호출하면 **200**이 오고 응답은 매번 `event: "message_delete"` 로 같다.
> 그런데 예약 메시지가 **도착할 때도 있고 안 할 때도 있다** — 동일 조건 5회 중 3회
> 도착(취소 실패). **응답만 보면 구분할 수 없다.**

이걸 모르고 "크론이 멈추면 알려주는 dead man's switch"를 만들면, 크론이 정상인데도
**절반 가까운 확률로 오탐**이 울린다. 일관되게 깨진 것보다 **간헐적으로 되는 쪽이 더
나쁘다** — 예측 불가능한 오탐은 알림 신뢰를 무너뜨려 진짜 경고까지 무시하게 만든다.

→ **"200이 왔으니 됐다"는 검증이 아니다.** 의도한 결과가 실제로 일어났는지를 본다.

→ 그리고 **표본 1~2회로 단정하지 않는다.** 이 건도 처음엔 2회 연속 "도착" 을 보고
"취소는 동작하지 않는다" 고 결론냈다가, 표본을 5회로 늘린 뒤에야 비결정적이라는 걸
알았다. **실패를 두 번 봤다고 "항상 실패" 가 아니다.** `doctor.mjs` 의 해당 검사가
3회 반복으로 되어 있는 이유다.

### 8. 플랫폼이 이미 해주는 것을 다시 만들지 않는다

Supabase는 정지 **1주 전에 경고 메일**을 보낸다. 즉 플랫폼 자체가 이미 dead man's
switch 역할을 한다. 감시견을 직접 만들기 전에 이걸 먼저 확인할 것.

## 권장 구성

```
1차   플랫폼 내장 크론 (예: Vercel Cron, 매일)
        → /api/cron/keep-alive   [시크릿 보호]

2차   외부 cron SaaS (예: cron-job.org, 매일)
        → /api/wake              [무인증·무해]
        → 실패 시 메일 알림 = 감시견

수동   알림의 실행 버튼 → /api/wake

안전망 플랫폼 자체 경고 메일
```

두 스케줄러의 **실패 모드가 독립**이다 — 플랫폼 장애·배포 실패 ↔ 외부 서비스 장애.
호출 출처는 `?via=` 로 구분해 로그에 남기면 어느 층이 실제로 돌고 있는지 보인다.

## 사용법

1. `providers/` 에서 쓰는 서비스의 제약을 확인한다
2. `recipes/` 의 파일을 복사한다
3. `node scripts/doctor.mjs` 로 **문서의 주장이 아직 유효한지** 확인한다

```bash
node scripts/doctor.mjs            # 공개 문서 기반 검사
NTFY_TOPIC=xxx node scripts/doctor.mjs --live   # 실제 동작까지 검사
```

## 기여

공급자 정책은 수시로 바뀐다. `doctor.mjs`가 실패하면 **문서가 낡았다는 신호**다 —
그 지점이 곧 기여 시작점이다.

- `providers/*.md` 의 `last-verified` 를 갱신하고 변경점을 적어 주세요
- 새 공급자(Neon·Render·Fly·Railway…)는 `providers/` 에 같은 양식으로 추가해 주세요
